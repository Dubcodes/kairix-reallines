# Kairix RealLines V1.4 development handover

Version: `0.0.7-dev`  
Branch: `wip/live-tuning-dot-lock`  
Starting point: `8b255f583229ca9d91c2c7dcf28090b874493075`

This work was developed and tested in the Windows source checkout. Nothing was installed on, copied to, restarted on or deployed to the Raspberry Pi. Pico firmware, encoder pin assignments, quadrature mathematics and the 63-byte wire protocol were not changed.

## 1. CPU and stationary-motion findings

Three concrete avoidable costs were found in source:

- Tracking and rig fingerprints were regenerated from unchanged static profile data in the approximately 200 Hz state path. They are now cached and invalidated by profile writes/refreshes. A Windows microbenchmark of 100,000 calls measured 1.227684 seconds for direct tracking-fingerprint generation and 0.009531 seconds for the cached accessor (128.8× for that isolated operation). This is not a Pi whole-process benchmark.
- Routine debug events previously reached disk synchronously. They now enter a bounded 4,096-event RAM queue, flush every second or 256 events, rotate at 2 MiB with three generations, and preserve important errors immediately. Normal shutdown and explicit bundle creation flush pending events.
- The development service's `--reload` process is an independent source of filesystem monitoring and CPU. The reversible operation-mode script can remove reload without reinstalling or changing data paths. It never restarts the service unless explicitly requested.

The previously observed approximately 114% worker CPU and 65% reload-process CPU remain historical Pi measurements. This checkout was not run on the Pi, so there is no honest post-change Pi CPU, memory, loop-jitter or SD-write result yet.

The reported stationary graphics jump was not reproduced on physical hardware during this pass. The new Tracking Stability recorder is therefore diagnostic rather than a claimed fix. It distinguishes Pico raw-count movement, mapping/pose movement and output-only movement; fixed-server-pose mode isolates the downstream publication/browser/display path. No deadband, smoothing or Pico noise filter was added.

## 2. Tracking and logging implementation

- Opt-in 10–60 second, 60,000-event RAM-only recorder.
- Accepted Pico session/sequence/timestamp, Pi receipt time, cumulative counts/deltas, acquisition axes/references/health, camera/render pose and publication/drop/freshness information.
- Live and fixed-server-pose modes; fixed pose is process/session-only.
- JSONL/CSV export only on request.
- Runtime wall/process CPU timing and loop-jitter summaries for acquisition, tracking and publication stages.
- Every-Sample Pico processing prunes obsolete queue entries on arrival and consumption without changing the cumulative-position safety model.
- Existing slow-WebSocket-client isolation remains intact.

Routine queued logs can be lost on sudden power failure. Profiles, layouts, sync settings, targets and calibrations remain persistent atomic files and are not moved to volatile storage.

## 3. Browser cadence and latency instrumentation

GFX, Preview and Control now report rolling 5-second and 30-second pose/frame rates, frame interval mean/p50/p95/p99, missed 50 Hz deadlines, render durations, pose reuse, visibility, WebSocket/polling mode and aggregate output-queue health. Each browser page instance has an ephemeral identity, preventing multiple GFX windows from overwriting one report. Unsupported pages emit no browser telemetry.

The metrics intentionally leave pose age and presentation timing unavailable when clocks or scan-out timestamps are not comparable. Browser `requestAnimationFrame`, 50 Hz WebSocket delivery and Canvas duration do not prove HDMI scan-out or end-to-end camera latency.

For OBS measurement, use a 1920×1080 50 FPS project and recording, a 1920×1080 Browser Source with custom FPS explicitly enabled at 50, the capture device's real 1080p50 format, zero RealLines delay, and a recorded repeatable start/stop motion. Compare the first camera-motion and graphics-motion frames. Report intentional graphics delay separately.

## 4. Dedicated HDMI output

The implementation reuses clean `/gfx` in a separate Cage/Wayland/Chromium service. It defaults to `HDMI-A-2` and `1920x1080@50.00`, discovers connectors via DRM sysfs, parses exact modes from `modetest`, and refuses an unverified connector/mode. Engineering exposes configuration, connected/mode status and allowlisted start/stop/restart/enable/disable actions. The privileged helper accepts only those actions for `kairix-reallines-hdmi.service`; there is no generic command or service endpoint.

Install during an authorised Pi maintenance window only:

```bash
cd /home/reallines/kairix-reallines
git fetch origin
git switch wip/live-tuning-dot-lock
git pull --ff-only origin wip/live-tuning-dot-lock
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
sudo ./installer/install-hdmi-output.sh
modetest -M vc4 -c
```

The installer adds Cage, Chromium, `wlr-randr` and libdrm tests, installs the launcher/helper/sudoers/unit, updates group membership, reloads systemd and deliberately leaves the HDMI service disabled and stopped. Review `/etc/systemd/system/kairix-reallines-hdmi.service`, `/etc/sudoers.d/kairix-reallines-hdmi` and `data/hdmi_output.json` before enabling.

Rollback:

```bash
sudo systemctl disable --now kairix-reallines-hdmi.service
sudo rm /etc/systemd/system/kairix-reallines-hdmi.service
sudo rm /etc/sudoers.d/kairix-reallines-hdmi
sudo rm /usr/local/sbin/kairix-hdmi-helper
sudo rm /usr/local/lib/kairix-reallines/kairix-hdmi-launcher
sudo systemctl daemon-reload
```

No boot configuration or desktop environment is changed. Actual KMS mode, VSync, scan-out cadence, CPU/GPU use, browser crash recovery, HDMI reconnect, capture-card acceptance and latency remain physically untested. There is no genlock, deterministic field alignment, 1080i50 qualification or key/fill claim.

## 5. Precision markers and calibration quality

- Four inward tapered wedges by default; optional three-wedge mode.
- Clear central measurement gap, configurable CSS-aware size and opacity, selected outer highlight and generous invisible hit area.
- Separate gold observation and blue prediction styles.
- A close matching blue wedge hides visually at a defined four-CSS-pixel threshold; neither coordinate changes.
- Calibration-only magnifier with adjustable scale, clear centre, existing keyboard nudge and numeric coordinates.
- Solver-derived per-marker ΔX/ΔY/total residual, image inclusion, manual/automatic origin and inclusion status.
- Per-view RMS/worst marker, captured pose/reference status and nearest-view diversity contribution.
- Review-only marker or observation exclusion solves copied data outside the live path and compares the result on all original observations. It never deletes a measurement or replaces accepted calibration.

Manual Dot Calibration data, target coordinates, observations and accepted solutions remain compatible. Old points without method metadata are treated as manual without rewriting them.

## 6. Vision-assisted calibration

The first stopped-camera implementation provides:

- Explicit session start/stop with no normal-operation capture.
- Manual PNG/JPEG import for offline teaching/detection.
- Password-protected OBS WebSocket v5 `GetSourceScreenshot` against an explicitly named camera-only source.
- Independently persisted target templates/identities in `data/vision_targets.json`.
- OpenCV constrained local template matching, subpixel response-peak refinement, second-peak ambiguity detection, confidence reporting and identity-collision rejection.
- Two OBS screenshots 250 ms apart plus encoder-count comparison for settling.
- One-job bounded worker off the async event loop; no frame stream or unbounded queue.
- Immutable image-time counts, reference UUIDs and camera context. Later camera movement does not cancel processing.
- Existing Dot editor review and normal backend observation persistence. Uncertain, ambiguous, invalid-tracking or unsettled detections cannot be saved as automatic observations.

OBS credentials are stored separately in `data/vision_obs_secret.json`, mode `0600` where supported, and omitted from status, static assets and diagnostic exports. RealLines never changes OBS scene/program state. OBS response time is not exposure time, and the stopped-frame check does not establish precise video/encoder synchronization.

Scale/rotation changes beyond the local template search, lighting variation, blur, lens distortion, repeated-looking markers, OBS buffering and real target confidence require physical validation. Manual Dot Calibration remains the fallback. Future local V4L2 capture can implement the same still-image interface.

## 9. Required physical validation before broadcast deployment

1. Record the six stability modes: both simulated, Pan physical/Tilt simulated, Tilt physical/Pan simulated, both physical, no GFX clients, and fixed server pose.
2. Correlate raw count excursions, mapped angles, camera pose and rendered pose before attributing jitter to an encoder or display.
3. Inspect 3.3 V pull-ups, common ground, cable routing and A/B signals with suitable instrumentation. Do not add filtering without a separate firmware approval/latency benchmark.
4. Compare reload and stable service modes after equal warm-up: process CPU, `/api/performance`, memory, loop jitter, queue age and SD writes.
5. Run OBS 50 FPS frame-by-frame motion tests at zero configured delay.
6. Install HDMI components only during maintenance; verify `HDMI-A-2`, exact 1080p50, reconnect, Cage/Chromium crash recovery, cursor hiding, frame cadence, CPU/GPU load and capture-card lock.
7. Teach the real measured target from the camera-only OBS source; test lighting, zoom, Pan-separated fixed-Tilt views, ambiguity rejection and manual correction.
8. Confirm accepted vision observations retain the captured reference UUIDs/counts after moving the camera and cannot bypass normal world-calibration acceptance.
9. Recheck manual Dot Calibration, current setup profiles/layouts, provisional/strict GFX policy and session reference requirements after service restart.

Until those checks are complete, V1.4 is a development branch, not a broadcast-qualified release.
