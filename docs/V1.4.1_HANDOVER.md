# V1.4.1 tracking jitter and HDMI corrections

## Safety and scope

This patch does not change Pico firmware, calibration mathematics, accepted world solutions, profiles, layouts, or graphics projection. It adds an optional Pi-side cumulative-count filter and scheduling diagnostics. Physical jitter is **not claimed fixed** until the hardware acceptance run below passes.

## Count filter

Engineering → Pico Data Processing provides three settings:

- **Off**: original cumulative counts are mapped directly.
- **Conservative**: five-sample median; nominal group delay is two processed samples (4 ms at 500 Hz, 10 ms at 200 Hz).
- **Experimental**: seven-sample median; nominal group delay is three processed samples (6 ms at 500 Hz, 15 ms at 200 Hz).

The Pico's cumulative counts remain available as raw input counts. Filtered/accepted counts are maintained separately. A persistent displacement is eventually accepted exactly, so this is not a deadband and does not discard cumulative fast movement. Changing filter mode, a Pico session change, or a disconnect clears filter history and requires fresh references. It never recalibrates or silently creates a reference.

The supplied short-recording observations were represented in an offline fixture covering isolated ±1 Pan, ±2 Tilt, ±1 Zoom, and grouped disturbances. The complete original 5,002-packet capture was not present in the repository, so the representative fixture must not be described as a bit-for-bit archival capture.

The fixture suite also evaluates a two-confirmation direction-consistency candidate against stationary disturbances, fast movement, stopping, and reversal. It is deliberately not exposed as a runtime profile because its stepwise response needs physical rig evaluation. Conservative and Experimental therefore remain the measured five- and seven-sample median candidates.

## Scheduling and diagnostics

HDMI discovery and systemd calls run in a dedicated one-worker executor, serialized by an async lock. Ordinary two-second UI status reads use cached connector discovery (30 seconds) and service status (5 seconds); `Refresh connectors` explicitly reruns both. Calibration marker drags now send a coalesced overlay-only WebSocket message rather than a full state snapshot.

The stability recorder's inactive path no longer calculates an extra render pose. Its small RAM prebuffer automatically retains two seconds before, and five seconds after, a large mapped Pan/Tilt change, reference identity change, tracking-validity change, scheduling gap of at least 40 ms, or slow blocking HDMI operation. Exports correlate raw and filtered counts, mapped values, pose/publication identity, validity, transport state, and server timing events.

## Encoder electrical checks

Before interpreting software results:

1. Confirm each Pico GPIO input is pulled up to **3.3 V**, never 5 V. Use one independent pull-up for every A/B signal.
2. Confirm Pi, Pico, encoder supply, and camera-rig grounds share a low-impedance common reference.
3. The E38S6G5-600B-G24N may be powered from the specified 5 V supply only when its A/B outputs are verified NPN open-collector. A push-pull or unknown output requires proper level shifting before the Pico.
4. Scope A and B at the Pico pins under stationary, slow, and fastest expected movement. Check high/low levels, rise time, ringing, crosstalk, and supply/ground noise.
5. Route A/B as short paired signal/ground runs away from motors, HDMI, switch-mode power wiring, and mains. Use shielded or twisted cable where practical; bond a shield at one end unless the rig grounding plan requires otherwise.
6. Verify the quadrature state sequence changes one bit at a time (`00→01→11→10→00` or reverse). Invalid two-bit transitions indicate wiring/noise or sampling problems; firmware V1 does not report these transitions.
7. Hardware filtering must be reviewed separately. A small Schmitt buffer or carefully selected RC network can improve edges, but an RC time constant adds edge delay and can erase valid high-speed transitions. Measure worst-case quadrature frequency before choosing values.

Any Pico firmware change, including invalid-transition counters or PIO filtering, remains a separately reviewed future task.


Also test with the display disconnected, an unsupported mode submitted, and Chromium terminated. Each must produce an actionable failure or automatic service recovery without affecting the main RealLines service.

## Acceptance test

1. Record 60 seconds stationary with filter Off, then Conservative, without touching calibration or references between comparable runs except where the filter change deliberately requires re-referencing.
2. Export JSONL/CSV and compare raw disturbances, filtered accepted counts, suppressed samples, mapped angles, tracking-validity transitions, acquisition/publication gaps, browser pose identity, rendered changes.
3. Move each axis one count slowly and confirm it eventually maps exactly. Run fastest expected moves, abrupt stops, and reversals; confirm final raw and filtered cumulative positions agree after the bounded settling delay.
4. Confirm large rendered jumps with constant raw and filtered counts are reported as downstream/state/render issues rather than hidden by the filter.
5. On HDMI, verify physical capture lock at 1920×1080p50, animation-frame cadence, missed deadlines, CPU/GPU load, reconnect, no-display behavior, Chromium recovery, and service state.

## Rollback

Prefer a normal revert commit on the shared branch. For an emergency locally controlled checkout, switch back to the recorded pre-patch SHA without force-pushing, reinstall requirements, and restart the development service. Preserve all data files.

```bash
cd /home/reallines/kairix-reallines
git status --short
git reset --keep 920cab85db1f75a757570d40143b52f13985d297
.venv/bin/python -m pip install -r requirements.txt
sudo systemctl restart kairix-reallines-dev.service
sudo systemctl status kairix-reallines-dev.service --no-pager
```

Do not push that emergency reset. For a shared or already-published branch, create and push a normal revert commit instead.

Disable/remove HDMI without touching RealLines data:

```bash
sudo systemctl disable --now kairix-reallines-hdmi.service
sudo rm -f /etc/systemd/system/kairix-reallines-hdmi.service
sudo rm -f /usr/local/lib/kairix-reallines/kairix-hdmi-launcher
sudo rm -f /usr/local/sbin/kairix-hdmi-helper
sudo rm -f /etc/sudoers.d/kairix-reallines-hdmi
sudo systemctl daemon-reload
```

Do not delete `data/hdmi_output.json`, profiles, layouts, calibration data, or vision-calibration data during rollback.
