# V1.4.2 tracking, processing and HDMI handover

## Scope and evidence boundary

Development started on `wip/live-tuning-dot-lock` at `21ba24ec28d0a90b4a1c20a80f434c5f19fdc7ba`. No Pi service, package, permission, calibration file or Pico firmware was changed. Software tests cannot establish that physical encoder jitter or 1080p50 HDMI is fixed.

## Confirmed software causes and corrections

The Dot Calibration UI still searched saved observations by encoder-count tolerance whenever no observation was explicitly selected. Crossing the approximately ±3 Pan/Tilt or ±8 Zoom thresholds could therefore change the gold-marker observation identity without an operator selection. Gold coordinates were not rewritten, but a different saved coordinate set could be displayed.

V1.4.2 removes proximity-based selection. A saved observation is shown only when explicitly selected, remains pinned while the camera moves, and is labelled historical/out of pose by the existing comparison. Matching tolerances now affect edit eligibility and vector/error presentation only. Overlay requests and browser delivery carry a monotonically increasing revision, so a late response cannot replace newer operator intent.

The stability recorder captures overlay revision, observation identity and coordinates, world identity, FOV source and published pose together. It classifies overlay changes at constant pose, world-state changes and FOV-only changes. Fixed FOV is session-only: it freezes rendered FOV while Pan/Tilt remain live and never persists a lens setting.

## Processing measurements

The profiler now reports acquisition/publication target and measured rates, missed deadlines, mean/p50/p95/p99/maximum wall and CPU stage times, process CPU, GC pauses, Pico queue/sample age, and WebSocket/browser cadence. Named timings cover source snapshot, mapping/camera pose, pose-history update, full snapshot and pose publication.

These are **Pi 4B acceptance targets**, not results measured by Windows CI:

| Measurement | Normal-load target |
|---|---|
| Acquisition | ≥198 Hz over 30 s at a 200 Hz target |
| Acquisition lateness | p95 ≤2.5 ms, p99 ≤5 ms, maximum ≤20 ms |
| Publication | ≥49.5 Hz over 30 s at a 50 Hz target |
| Publication lateness | p95 ≤5 ms, p99 ≤10 ms, maximum ≤40 ms |
| Browser cadence | 49–51 FPS, p95 interval ≤22 ms, p99 ≤30 ms |
| Missed browser deadlines | ≤1 per 5 s after warm-up |
| Source sample age | p95 ≤10 ms in Latest Snapshot mode |
| Output queue | no critical overflow; obsolete pose coalescing is allowed |

Run each workload for at least 60 seconds after a 10-second warm-up: GFX only; Engineering + GFX; Calibration + Engineering + GFX; stability recording + GFX. Export `/api/performance`, browser diagnostics and stability JSONL for each run. If a threshold fails, use the named p99/max stage and automatic trigger as evidence; do not raise rates to hide it.

No before/after Pi benchmark was run in this pass. Field reports of approximately 95, 179–191 and 200 Hz came from different sessions and remain non-comparable.

## Encoder and power investigation

The existing Off/five-sample Conservative/seven-sample Experimental filters remain the only filters. Raw cumulative counts remain separate and genuine displacement converges exactly. Default remains Off. The reconstructed fixture demonstrates impulse rejection in software, but is not a physical capture and does not prove an electrical cause.

Engineering now separates current `vcgencmd get_throttled` flags from historical-since-boot flags. The read-only query is cached, single-flight and outside the event loop. RealLines never clears flags or reboots. Bits 0–3 describe current conditions; bits 16–19 describe conditions observed since boot. Historical undervoltage does not prove a current fault, and a zero current flag does not prove the earlier supply/cable/ground condition was sound.

Hardware work still required: record flags before reboot; inspect Pico session/uptime and UART errors; compare simultaneous raw-axis disturbances; test Off and Conservative under stationary, one-count, fast, reversal and abrupt-stop motion. Only an authorized reboot can provide a fresh post-supply-change baseline.

## HDMI seat architecture

The supplied logs identify seat acquisition as the confirmed startup failure: Cage could not access `/run/seatd.sock`, could not acquire a VT, and never created Wayland.

The installer now installs seatd, creates a dedicated `kairix-seat` group, configures the seatd socket for that group, and grants only the RealLines account membership. Cage explicitly selects seatd with `SEATD_VTBOUND=0`; Chromium and RealLines remain unprivileged. The HDMI unit requires seatd, drops the unused input group, and limits failures to three starts per 60 seconds with a five-second retry.

The launcher records atomic connector/seat/compositor/mode phases beside `hdmi_output.json`. Engineering distinguishes stopped, waiting for connector, seat failure, compositor failure, mode confirmation, browser connection and rendering. A transient systemd `active` state is not treated as successful rendering. Connector waits are bounded, exact 1920×1080@50.00 DRM validation remains mandatory, and no 60 Hz fallback exists.

This follows seatd/libseat's group-owned Unix socket, explicit backend and headless VT-unbound behavior. It does not make DRM devices, TTYs or the socket world-writable and does not run Chromium as root. It is covered by simulated tests only; DRM ownership, captured cadence and latency require physical acceptance.

```bash
ssh reallines@192.168.0.41
cd /home/reallines/kairix-reallines
git status --short
tar -C /home/reallines/kairix-reallines -czf /home/reallines/reallines-data-before-v1.4.2.tgz data

git switch wip/live-tuning-dot-lock

git rev-parse HEAD
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pytest tests -q
```

Install the reviewed HDMI/seat files; HDMI autostart remains disabled:

```bash
sudo ./installer/install-hdmi-output.sh
id reallines
systemctl status seatd.service --no-pager
stat -c '%A %U %G %n' /run/seatd.sock
sudo -u reallines test -r /run/seatd.sock
sudo -u reallines test -w /run/seatd.sock
modetest -M vc4 -c
systemctl is-enabled kairix-reallines-hdmi.service || true
systemctl is-active kairix-reallines-hdmi.service || true
sudo systemctl restart kairix-reallines-dev.service
vcgencmd get_throttled
```

After Engineering confirms HDMI-A-2 and 1920×1080@50.00, manually test:

```bash
sudo systemctl start kairix-reallines-hdmi.service
systemctl status kairix-reallines-hdmi.service --no-pager
journalctl -u seatd.service -u kairix-reallines-hdmi.service -n 200 --no-pager
cat data/hdmi_runtime_status.json
```

Do not enable HDMI at boot until capture confirms clean 1080p50 graphics and restart/disconnect/browser-crash recovery passes.

## Rollback

```bash
sudo systemctl disable --now kairix-reallines-hdmi.service
cd /home/reallines/kairix-reallines
git status --short
git reset --keep 21ba24ec28d0a90b4a1c20a80f434c5f19fdc7ba
.venv/bin/python -m pip install -r requirements.txt
sudo systemctl restart kairix-reallines-dev.service
```

To remove only the seat override and restore the distribution unit:

```bash
sudo rm -f /etc/systemd/system/seatd.service.d/kairix-reallines.conf
sudo systemctl daemon-reload
sudo systemctl restart seatd.service
sudo gpasswd -d reallines kairix-seat || true
```

Software rollback does not require deleting saved observations or accepted calibration.
